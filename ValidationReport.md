# Validation Report: Policy Management BFF API

**Date:** 2026-11-23
**Scope:** `backend/` — `openapi.yaml`, `PolicyController`, the layer structure, and the integration tests
**Baseline:** commit `b14f663`, plus the changes in this report (not yet committed)

---

## 1. API Contract Compliance

**Rating: High.** All four endpoints, every query parameter and every response field in `openapi.yaml` are implemented with matching names, types and status codes. The differences found were edge cases in validation.

### Verified as compliant
- `GET /api/v1/policies`, `GET /api/v1/policies/{id}`, `PATCH /api/v1/policies/flag` and `GET /api/v1/policies/summary` all match the spec's paths, methods, operation IDs and response shapes.
- `status` and `lineOfBusiness` query values are accepted as API labels (`Active`, `A&H`) through `EnumConverterConfig`. An unknown label returns a 400.
- Errors (400 and 404) are returned as `application/problem+json` (RFC 7807) through `GlobalExceptionHandler`.
- `PolicyResponse`, `PagedPolicyResponse`, `PolicySummaryResponse` and `BulkFlagResponse` contain every required field.

### Gaps found

| # | Gap | Status |
|---|---|---|
| 1 | A negative `page` was silently changed to 0 instead of returning a 400, despite `minimum: 0` in the spec. | **Fixed:** now returns 400 |
| 2 | `size < 1` silently fell back to 20, and `size > 2000` was silently capped. Neither returned a 400. |**Fixed:** now returns 400; `maximum: 2000` added to the spec |
| 3 | `sort` accepted any field on the JPA entity, and the sortable fields were not documented. | **Fixed:** allowlist of 9 fields, now documented in the spec |
| 4 | `BulkFlagRequest.policyIds: [null]` passes validation, and its outcome is not defined. | Open |
| 5 | The catch-all 500 ProblemDetail response is not documented in the spec. | Open |
| 6 | Some `@Operation`/`@ApiResponse` descriptions are worded slightly differently from the YAML. This only matters if the docs generated by Springdoc are compared with `openapi.yaml`. | Open (cosmetic) |

## 2. Architecture Conformance

### Checks from CLAUDE.md

| Check | Result |
|---|---|
| No Spring or JPA annotations in `domain/model/` | **Pass:** `Policy`, `PolicyStatus` and `LineOfBusiness` import only `java.*` |
| No JPA entity types in `service/` or `api/` | **Pass:** `PolicyEntity` is referenced only inside `infrastructure/persistence/` |
| Domain objects not exposed directly by the API | **Pass:** everything goes through `PolicyMapper` to DTOs|

### Softer violations found (before the fix)

| # | Violation | Severity | Status |
|---|---|---|---|
| 1 | The `Pageable` from the request was passed straight to `jpaRepository.findAll(spec, pageable)`, so `?sort=` was matched against `PolicyEntity` field names. Renaming an entity field would silently change the public API. | **Medium-High** | **Fixed** |
| 2 | The service port and `PolicyService` depended on Spring Data `Page` and `Pageable`. | Medium | **Fixed** |
| 3 | `GlobalExceptionHandler` (API layer) caught Spring Data's `PropertyReferenceException`. | Low | **Fixed** (handler removed) |
| 4 | `PolicyMapper` depended on Spring Data `Page`. | Low | **Fixed** |
| 5 | Web MVC configuration (`EnumConverterConfig`, `CorsConfig`) sits in `infrastructure/config/` rather than `api/`. | Low | Open |
| 6 | `PolicyMapper.toDomain(PolicyResponse)` is never called. | Nit | Open |

### Fix applied
- **Added** `service/port/PageQuery` and `service/port/PageResult` as paging types with no framework dependency. `PageQuery` rejects `page < 0` and any `size` outside 1–2000.
- **Added** `service/InvalidQueryException`, mapped to 400. A plain `IllegalArgumentException` couldn't be used: when thrown from a `@Repository`, Spring's persistence exception translation rewrites it into `InvalidDataAccessApiUsageException`, which turned an expected 400 into a 500 during testing.
- **Changed** `PolicyRepositoryAdapter` to translate `PageQuery` into `PageRequest`/`Sort` through a `SORTABLE_PROPERTIES` allowlist that maps API names to entity names. Any other sort property now returns a 400.
- **Changed** `PolicyController` to take `page`, `size` and `sort` (`property[,asc|desc]`) as plain query parameters. A malformed `sort` returns a 400.
- **Removed** the `PropertyReferenceException` handler.

**After the fix:** `grep` finds no `org.springframework.data`, `jakarta.persistence` or `infrastructure.*` imports in `service/`, `api/` or `domain/`.

**Behaviour changes for API client
- Out-of-range `page` or `size` values now return a 400 instead of being silently corrected.
- Sorting on `currency`, `underwriter`, `createdAt`, `updatedAt` or `id` now returns a 400. The frontend never offered these fields.
- Only a single `sort` parameter is accepted, matching the spec. Spring previously accepted several.

## 3. Test Coverage

**Rating: Medium.** All four endpoints and their main 200, 404 and 400 paths are tested end-to-end against PostgreSQL (Testcontainers, Flyway seed of 210 rows). Gaps remain in validation of bad input, and until this change one core business rule had no meaningful check.

| # | Endpoint | Scenario not covered | Status |

| 2 | `GET /policies` | 400 for invalid `page`, `size` or sort direction | Covered by the unit test only (`PolicyControllerTest`, mocked service) |
| 3 | `GET /policies` | 400 for a malformed date (`effectiveDateFrom=not-a-date`) | Open |

| 7 | `PATCH /flag` | Malformed JSON body, or `[null]` in `policyIds` | Open |
| 8 | 400s for `GET /policies/{id}` and `GET /policies` | Two tests assert only the status code, not that the body is `application/problem+json` | Open |

### Tests added

**Integration test (`PolicyControllerIntegrationTest`):**
- `summaryReportsPremiumPerLineOfBusinessPerCurrencyWithoutCrossCurrencySumming` computes the expected totals from the database (`SUM(premium_currency`). It then checks that the response has exactly the four line-of-business labels (including `A&H`), exactly the expected currencies under each, and a matching total for each currency. It first asserts that the seed data has more than one currency, so the test can catch summing across currencies.
- `entityFieldOutsideSortAllowlistIsRejectedWithBadRequestProblem` was added with the architecture fix (`sort=underwriter` returns 400).

**Unit tests (`PolicyControllerTest`):**
- Sort with no direction defaults to ascending.
- A parameterised test covering five invalid inputs (`page=-1`, `size=0`, `size=2001`, a bad direction, too many sort segments). Each must return a 400 ProblemDetail without calling the service.

## 4. Summary

**Overall assessment: good, ready to ship once these changes are reviewed and committed.**
- The API matches its contract closely.
- The hexagonal layering now holds at the import level as well as the annotation level: the service and API layers no longer depend on Spring Data, and the public sort contract no longer depends on JPA field names.
- The integration tests run against a real database rather than mocks, and now verify the summary's per-currency premium rule.
- What remains is mostly validation of bad input and a few cosmetic or organisational items. No correctness defects are known.

**Recommended next step:** move the 400-path tests to the integration suite. Specifically: invalid `page`/`size`/`sort`, a malformed date, an unknown `lineOfBusiness`, and malformed JSON or `[null]` in `PATCH /flag`. Make every 400 test use `expectProblem(...)` so it also checks the `application/problem+json` body. Then document the 500 response, and decide whether `[null]` gets a 400 (for example, `@NotNull` on the list elements). These paths depend on Spring's argument binding, the exception handler and persistence exception translation working together, and this review already found one case (a 400 becoming a 500) that only showed up end-to-end.
